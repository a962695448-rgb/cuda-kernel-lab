# 01 SGEMM：从朴素版本到双缓冲

代码：`src/sgemm.cu`。行主序，C = A·B，A 是 M×K，B 是 K×N。

## 版本对比

| 版本 | 核心改动 | 解决了什么问题 | 还剩什么问题 |
|---|---|---|---|
| v0 朴素 | 一个线程算 C 的一个元素 | — | 每算一个元素就要从显存读 2K 个数；数据完全没有复用 |
| v1 共享内存分块 | block 先把 32×32 的 A、B 小块搬进共享内存 | 每个数从显存读的次数从 K 次降到 K/32 次 | 每次乘加要读 2 次共享内存，瓶颈转移到共享内存带宽 |
| v2 一维线程分块 | 一个线程算同一列的 8 个结果 | 读 1 个 B 值，配合 8 个 A 值重复使用 | A 仍然每次都从共享内存读 |
| v3 二维线程分块（8×8） | 每个线程把 8 个 A、8 个 B 读进寄存器，做 8×8 次外积 | 读 16 个数，换 64 次乘加 | 全局内存一次只读 4 字节；A 的共享内存读取不连续 |
| v4 向量化 | float4 读全局内存；A 在共享内存里转置存放 | 指令数更少；内层循环读 A 时地址连续 | 加载和计算是串行的：先等数据到，再开始算 |
| v5 双缓冲 | 共享内存开两份，计算第 k 块时预取第 k+1 块 | 显存读取延迟被计算掩盖；每轮只需一次 `__syncthreads` | 离 cuBLAS 还有差距：没有用 warp 级分块，也没有用 `cp.async` 异步拷贝 |

## 必须会算的数

- **v1 的数据复用**：一个 32×32 的 block 每轮读 2×32×32 个数，做 32×32×32 次乘加。每读一个数，做 16 次乘加。
- **v3 的寄存器复用**：每个线程每步读 TM+TN = 16 个数，做 TM×TN = 64 次 FMA，每读一个数做 4 次 FMA。v2 是 (1+8) 个数换 8 次，约 0.9 次。
- **block 规模**：v3 到 v5 的 BM=BN=128、BK=8，一个 block 256 个线程，每个线程负责 64 个结果。共享内存用量：v3/v4 是 2×128×8×4 B = 8 KB，v5 双缓冲翻倍到 16 KB。

## 面试高频问题

**Q1：为什么一个线程算 8×8，而不是 4×4 或 16×16？**（寒武纪面经原题）
- 4×4：每读 8 个数做 16 次 FMA，复用率是 8×8 的一半，共享内存带宽会先成为瓶颈。
- 16×16：光累加器就要 256 个寄存器，超过单线程 255 个寄存器的上限，会溢出到 local memory（实际在显存里），性能断崖式下降。
- 8×8：64 个累加器加上 16 个暂存值，大约 100 多个寄存器，放得下；256 线程的 block 用掉约 3 万个寄存器，一个 SM 还能同时驻留 2 个 block。另外 8 刚好是两个 float4，便于向量化读写。
- 结论：这是**数据复用率**和**寄存器压力 / occupancy** 之间的平衡点。真实答案还取决于具体的卡，用 `--ptxas-options=-v` 看寄存器数量，用 ncu 看 occupancy 来验证。

**Q2：为什么要把 A 转置存进共享内存（v4）？**
- 内层循环里，一个线程要读 A 的同一列、连续 8 行。不转置时这 8 个数在共享内存里相隔 BK 个 float；转置后变成连续地址，编译器可以用 128 位的 `LDS.128` 一次读 4 个。
- 代价：写入转置位置时会有少量 bank conflict（2 路），但写只发生一次，读要重复很多次，划算。

**Q3：双缓冲为什么能变快？有什么代价？**
- 没有双缓冲时："读显存 → 同步 → 计算 → 同步"是串行的，显存延迟（几百个周期）全部暴露出来。
- 双缓冲时：先发出下一块的读取请求，结果暂存在寄存器里，同时计算当前块，算完再写进另一份缓冲区。延迟就被计算掩盖了。
- 代价：共享内存翻倍、寄存器变多，可能降低 occupancy。所以收益要用 ncu 的 stall 指标来验证（看 `long_scoreboard` 停顿是否下降）。

**Q4：离 cuBLAS 还差在哪？**
- 少了 warp 级分块：让一个 warp 负责一块连续区域，减少共享内存 bank conflict，提高寄存器复用。
- 少了 `cp.async`（Ampere 起支持）：数据可以绕过寄存器直接从显存进共享内存，配合多级流水线（multi-stage pipeline）。
- 少了针对不同形状的 autotuning，以及 SASS 级别的指令调度。cuBLAS 和 CUTLASS 都有这些。

**Q5：怎么验证结果正确？**
- 用 cuBLAS 的结果做参考，逐元素比较，误差容忍 atol=5e-3、rtol=1e-3。
- FP32 累加的顺序不同，结果不会逐位相同；误差会随 K 增大，大约按 √K 增长。

## 实测结果（RTX 5090，CUDA 12.8，2026-10-16 实测；数据来自 `results/`）

M=N=K=4096，cuBLAS 为 69.3 TFLOPS（关闭 TF32 的纯 FP32）：

| 版本 | GFLOPS | 占 cuBLAS | 每线程寄存器数 |
|---|---|---|---|
| v0 朴素 | 6,452 | 9.3% | 40 |
| v1 共享内存 | 9,345 | 13.5% | 38 |
| v2 一维分块 | 28,608 | 41.3% | 49 |
| v3 二维分块 8×8 | 48,376 | 69.8% | 128 |
| v4 向量化 | 50,403 | 72.8% | 103 |
| v5 双缓冲 | **56,034** | **80.9%** | 119 |

几点观察（面试时可以直接讲）：
- **最大的一跳是 v2 → v3**（41% → 70%）：线程级的寄存器复用（每读一个数做 4 次 FMA），比 block 级的共享内存复用更关键。
- **小矩阵上 v3、v4 反而比 v2 慢**：1024³ 时 v3 只有 39.7%，v2 有 47.2%。原因是 v3 的 block 是 128×128，1024² 的矩阵只切出 64 个 block，而 5090 有 170 个 SM，超过一半的 SM 闲着（wave quantization，波次量化）。v2 的 block 是 64×64，有 256 个 block，能把 GPU 填满。所以 cuBLAS 会针对不同形状选不同的 tile 尺寸。
- **v4 的寄存器比 v3 少**（103 对 128）：float4 读取和转置后的连续地址，让编译器用更少的指令和寄存器完成同样的工作。
- 5090 的 FP32 峰值约 104.8 TFLOPS（170 SM × 128 FP32 单元 × 2 × 2.41 GHz）；cuBLAS 达到峰值的 66%，v5 达到 53%。
- 正确性：全部版本与 cuBLAS 的最大绝对误差为 3.8×10⁻⁴（4096³），在容差内。
